# AGENTS.md

Guidance for AI coding agents (and humans who like the detail) working in this repo.

## What this is

**Meridian Shards** is a faithful browser port of the Meridian 59 client. It talks to **our own** server, built from our fork of the Server 104 source (`shards-server`, which `server/src` links to), through a WebSocket-to-TCP gateway. Only our client and our server have to work: original Windows clients and other servers aren't supported, though the original's source and behaviour stay our reference (ADR 0001 decisions 3 and 4, changed 2026-10-15). It's the third experiment beside the UE remaster (`E:\2026_Experiments\meridian-unreal`) and the Roblox spin-off "Fantasy Blocks".

## Hard rules

- **The name is "Meridian Shards".** Never use "104" in any product name, branding, UI text or package name. Referring to the "Server 104" *code* in docs is fine.
- **GPLv2.** Everything here is GPLv2 (see `LICENSE`). We port `clientd3d` C logic directly.
- **Code may go from this repo to the UE remaster** (`meridian-unreal`), which is GPLv2 too, with an Unreal Engine linking exception (its `LICENSE-EXCEPTION.md`). **Except code ported from the Meridian 59 source**, which follows the original's own logic (`roo.ts`, `bgf.ts`, `roomGeometry.ts`, `movement.ts`, `chess.ts` and the like). That's the original authors' code, which the exception can't cover, so the remaster re-implements it from written-down facts. Code that only implements wire formats, such as `packages/protocol`, isn't a port. The remaster's AGENTS.md has the full rule. Code from the remaster may come here freely.
- **Raw art never goes in git.** That covers `.bgf`, `.roo`, `.rsb`, `.ogg`, `.wav`, `.bmp` and extracted PNGs. They're served from the git-ignored asset build.
- **The user makes the commits.** Don't `git commit` or push unless explicitly asked. Finish by listing the changed files.
- **Ask before downloading or installing anything** (npm packages, tools, client builds), stating what it is, the source and the size.
- **`meridian-unreal\Server-104` is a read-only reference.** Our server is the shards-server repository; `server/src` is a junction to it (`server/link-src.cmd`). Server and Kod changes are made and committed there, not here.
- **Own server only.** Never point any client or tool at the live 104 server.

## Running the local stack

```bash
npm install                 # workspaces + dependencies
server\build.cmd            # first time, or after Kod/C changes (VS 2026 x86 toolset)
server\setup-run.cmd        # creates run folders, installs server/config/blakserv.cfg
npm run sounds              # our CC0 ambient recordings into dist/sounds (once; npm run assets copies them)
npm run assets              # dist/assets from our server build + the installed 104 client
npm run dev                 # blakserv (if not running) + gateway (ws://localhost:8059) + Vite (http://localhost:5173); says if Kod, rooms or dist/assets are out of date
npm run dev -- --rebuild    # the same, building what's out of date first (server\build.cmd Bresource Bkod, npm run assets)
npm run dev -- --editor     # the same, plus the room editor's web build (../meridian-editor, http://127.0.0.1:5174)
npm run headless -- --user shardbot --pass shardbot --walk "8.5,7.5 9.05,6.5" --go --stay 10
npm run smoke               # headless shardbot: log in, enter, stay 10 s, quit (is the stack up?)
npm run soak                # headless shardbot walking back and forth for 5 min (LCG and token soak)
node tools/headless/friend.ts --user shardpal --pass shardpal --add Shardbot   # a scripted friend (accepts requests; --follow, --pet, --walk/--go to lead)
npm run check               # typecheck + lint + tests
npm run test:watch          # Vitest in watch mode
npm run icons               # remake the app icons and favicons from tools/icons/emblem.png
npm run desktop             # the dev stack plus the desktop app on Vite (F12 for DevTools)
npm run desktop:start       # the desktop app as it ships (app://shards), unpackaged
npm run desktop:build       # an unpacked build in apps/desktop/dist/win-unpacked
npm run desktop:dist        # installers + latest*.yml for this OS, with dist/assets inside
npm run desktop:release     # the same, uploaded to a draft GitHub release (CI does this on a v* tag)
npm run release -- 0.2.0     # bump, commit, tag and push; CI builds all three OSes and publishes v0.2.0
npm run android:run         # build the client and the debug APK, install it on the phone or emulator, adb reverse 5173, launch
npm run android:run -- --no-build --device emulator-5554   # reinstall and relaunch only, on one of several devices
npm run android:run -- --bundle   # with the game files in the APK (dist/assets, ~380 MB), as release builds have them
npm run android:run -- --release  # the signed release APK as players get it (uninstalls a debug build first: another key)
npm run android:sync        # build the client and copy it into apps/android/android (then build in Android Studio)
npm run android:web-bundle  # the page by itself as a release's update zip, in dist/ (after android:sync)
```

- **Android** needs Android Studio (the SDK; `apps/android/android/local.properties` says where, e.g. `sdk.dir=J\:/AndroidSDK`) and a JDK 21 for Gradle (`org.gradle.java.home` in `~/.gradle/gradle.properties`). Android Studio's own JDK 25 can't run the template's Gradle 8.14; in Android Studio, set Settings → Build Tools → Gradle → Gradle JDK to the JDK 21 too. Debug builds list "Local (dev)" (`http://localhost:5173` on the device, through `adb reverse`) next to the VM; pick it on the login screen.

- Our build of the original Windows client, kept as a reference only (it isn't supported for play): `server\build.cmd Bclient Bmodules`, then `server\setup-client.cmd`, then run `server\src\run\localclient\meridian.exe /U:<user> /W:<pass> /H:localhost /P:5959`. Never use the installed 104 client's `rsc0000.rsb` or rooms with our server.
- **blakserv by itself**, from the shards-server folder (`server/src`; no `npm install` needed): `npm start` (its own window, waits for the ports), `npm stop` (`terminate save`), `npm run restart`, `npm run status` (the ports and `who`), `npm run logs` (the end of `channel/error.txt` and `debug.txt`), and `npm run maint -- "<command>"` (`tools/server.mjs`). `npm run dev` here still starts it when it isn't running, and leaves it running.
- blakserv takes about 35 s to load a fresh game. It's ready when ports 5959 and 9998 listen. Don't send it maintenance commands before then: on the hosted Linux server, a `show status` during startup hung blakserv's main loop, and every login waited forever until it was restarted (`deploy/README.md`). Clients give up on their own now: `GameSession`'s `LOGIN_TIMEOUTS` (15 s for the socket to open, 15 s for the server's first word, 45 s to the character list) end the login with a message on the login screen and let go of the connection.
- `npm test` runs Vitest. The format tests read the real files in `dist/assets` and are skipped if you haven't built the assets. So is `tools/assets/artRefs.test.ts`, which checks that every `.bgf` and `.ogg` our code names (ambient life, critters, pets, rocks) is in the asset build and that critters' and pets' cycles fit their art: our server can remove a monster or restyle its art (iconforge) under us.
- **The run folder** is shards-server's `run/server`. It started a fresh game on 2026-10-15, when `server/src` became the junction; the test accounts were made again then. The old Server 104 copy and its save are in `server/src-104`, kept for reference. The four new-game errors in `channel/error.txt` (`GetStatResetTokenLife`, `GetPlayerMarketItems`, `C_MoveSectorBSP`, `IsChaosNightActive`) are upstream's and appeared on Server 104 too.
- **`npm run assets` needs `clientd3d/debug/pal.c`** for exact light-based xlats; without it, it warns and guesses. `Bclient` fails in the shards-server tree (its `login.c` is git-ignored; only `login.c-example` ships), so make just that file: in a VS developer prompt, run `nmake -nologo debug=1 debug\pal.c` in `server\src\clientd3d`.
- The room viewer is at `http://localhost:5173/?rid=<RID>`, in development only (`host.ts devPagesEnabled`: Vite's dev server); no build players get has it or the login screen's link to it. In dev, `window.shards.roomScene.lookFrom(row, col, eyeHeight, compassYaw)` places the camera, which is handy for comparing against original-client screenshots.

## Code conventions

- TypeScript run directly by Node 24 (type stripping), so use **erasable syntax only**: no `enum`, no constructor parameter properties, no `namespace`. Use `as const` objects instead of enums. Import with explicit `.ts` extensions.
- Keep `packages/protocol` and `packages/formats` free of Node APIs, so they run in the browser.
- When porting C, cite the source as `file:line` in a comment. Keep wire formats byte-exact, and decode strings as Latin-1 one byte per char. Never use `TextDecoder("latin1")`, which is windows-1252 in browsers.

## Known traps

- The redbook token needs the **same `rsc0000.rsb` the server built**. A wrong string shows up as "first packet after each echo is fine, the second has a garbage type".
- Every game message steps the LCG. Never drop or reorder outgoing game messages after they've been encoded.
- Fresh connections start in login mode (`AP_GETLOGIN` arrives first). The beacon handshake is only for resyncs.
- `BP_CHARACTERS` flag `1` means "needs creation", whatever `blakserv/game.c` says in its comment.
- The maintenance port ends commands with CR (`\r`), not LF.
- The server snaps you back with `BP_MOVE` when a move lands outside the room. Exits need `BP_REQ_GO` while standing on the exit square.
- **Rendering: trust the C code over the Python tools.**
  - Grid textures are stored transposed in the `.bgf`, and the client's s/t coordinates already account for that, so upload the pixels as stored and use u = s, v = t.
  - Wall `length` and the texture offsets are in Kod units (64 per square); heights and positions are in client units (1024 per square). `PETER_FUDGE` (16) bridges them.
- Client coordinates are x east, y south, z up. The scene uses X = x, Y = z, Z = y, in squares, which mirrors handedness, so `RoomView` reverses the triangle winding.
- The room checksum the server sends goes through a 28-bit Kod integer. Compare the low 28 bits only.
- The Browser pane throttles `requestAnimationFrame` while it's hidden, so FPS readouts there are meaningless. Time `renderer.render` instead.
- **Sprites:** each object's base bitmap and overlays are composited on the CPU into one palette-index image (with each part's xlat applied), then drawn as a single billboard. That keeps exact palette colours and avoids z-fighting between coplanar overlays. The image is on the base bitmap's grid; a face (a head with eyes, nose, mouth or toupee, finer art than the body) would lose rows there, so in the world it comes as a second, small image up to 4× finer over the face's box (`sprites.ts faceApart`, `Composite.face`), which the sprite shader draws there instead. Making the whole figure 4× finer cost about 19 ms at every step a townsperson took. Portraits and icons (`icons.ts`) still make the whole picture finer: they're made once.
- **Handedness:** the D3D client's projection uses a *negative* horizontal FOV (`FovHorizontal`), which mirrors its left-handed view back. Our right-handed scene with X = x, Y = height, Z = y matches what players see, both the world and the sprites (bitmap column 0 on the left). Don't "fix" it.
- **Looking** goes through `GameView`'s `lookAt(id, buttons)`: it sets the next description's DESC_* buttons (`dialog.c SetDescParams`), then sends `BP_REQ_LOOK`. The answer is `BP_LOOK`, or `UC_LOOK_PLAYER` for a player (the Player Description, with their own words and web page). A ¶ (0xB6) splits an inscription into pages.
- **Options** come from `apps/client/src/game/settings.ts`, edited in the game's ☰ menu, laid out like the original's windows (`ui/OptionsDialogs.tsx`):
  - **Preferences** is `client.rc IDD_SETTINGS` without Web Browser (O or F10). Options we don't implement yet are kept anyway and shown in italics; list them in `docs/missing-features.md`.
  - The Game Options and "Can attack innocent players" live on the **server**: `UC_REQ_PREFERENCES` on entering, `UC_RECEIVE_PREFERENCES` back, `UC_SEND_PREFERENCES` (the `CF_*` flags) on OK.
  - **Configuration** is the Bind Editor (`m59bind.exe`): its Options box as the first tab (ours, for room: Quick Chat, Always Run, Attack On Target, Dynamic Lighting and our own options, in Playing, World and Interface boxes), the six key tabs plus our Interface tab, and Mouse; Restore Defaults, OK and Cancel along the bottom.
  - Bindings take Alt or Ctrl, and mouse buttons as `Mouse0` (left), `Mouse1` (right), `Mouse2` (middle), like `config.ini`. Unbound F1–F12 send the hotkey aliases.
  - **Actions** has Who (ignoring players), groups (`BP_SAY_GROUP`), hotkey and command aliases, and the guild window (from the server: `UC_REQ_GUILDINFO`). The ☰ menu has the same as an Actions submenu; no Spells menu (the Spells tab has a search) and no emotes (a click on our face shows the Quick Emotes, as Q does: `GameView toggleEmotes`). Logout timer… isn't on the phone's menu. No Mail… either: the mailbox at the map's corner (or the Classic toolbar), F11 (its hotkey alias) and typed `mail` open it.
  - Settings saved by older versions are migrated in `migrate()`; bump `SETTINGS_VERSION` when a saved field changes meaning.
- **Controls**, the modern preset:
  - The mouse is never captured but while the right button is held: hold it and drag to turn the view (orbit the chase camera), the lock asked for on the press (the user's gesture) and let go on release; the drag threshold (`RIGHT_DRAG_SLOP`) counts `movementX/Y`, since the locked cursor doesn't move. A right click without dragging examines, on release (`gameScene.ts rightDrag`). Both interfaces on the desktop; the phone drags with a finger. The original's mouselook (a click, Mouselook Toggle) is gone, and saved bindings for it are dropped in `migrate()`.
  - WASD or arrows to move (left/right arrows turn), Shift to run (or walk, with Always Run), Space to open a door.
  - Left click targets players and monsters only (Select Target, `gameuser.c UserAttack`); E attacks; `]` `[` `\` Esc pick the next, previous, yourself or no target; R looks at the target. Only the target gets the halo; hovering just changes the cursor.
  - Right click looks (Examine, in both presets): the description dialog (`ui/LookDialogs.tsx`, `dialog.c`), with the buttons the original gives it (Get/Use close by, Drop/Use/Unuse in the inventory). Right click on the inventory, the spell list or your portrait looks too.
  - Picking up: drag an item from the view onto the inventory, the dialog's Get, or G or F (Pick Up; settings version 15 added G) / typing `get`, which takes what's close by (a list when there are several). Double click (or double tap) activates; on a shopkeeper or vault keeper (`OF_BUYABLE`) it opens their Buy or Withdraw window (`GameView askTrader`: BP_REQ_WITHDRAWAL first, since only a vault keeper answers it, then BP_REQ_BUY); on someone who only takes things (`OF_OFFERABLE`, not attackable: a banker) it opens Deposit. Typing `buy` or `offer` deals with the nearest shopkeeper.
  - Several objects under the cursor: a list asks which one (`lookdlg.c DisplayLookList`), for looking, targeting, activating and getting. R (Look) or typed `look` lists everything in view.
  - Containers (storage boxes in rented rooms): Inside in the description, a double click, or dragging the box to the inventory shows what's in it, to take out with amounts; typed `put` stores inventory items in one close by.
  - To try containers on our server: `node tools/maint/maint.ts "create object StorageBox"`, then `"send object <room id> NewHold what object <box id> new_row int <r> new_col int <c>"` (the room is the player's `poOwner` in `show object <player id>`), and `"send object <box id> Delete"` afterwards.
  - T, Y, B and ; start a tell, yell, broadcast or emote; Enter chats. In sewers and swamps they swim in shallow water, drawn at its surface (`z`), since ObjectsView sinks objects to the bottom as the original does. A click (Select Target with nothing real under the cursor, a tap on the phone) or an attack with nothing real in reach (`squishAhead`) kills one at once: `Critters.squish`, its death sound at 35% (`playAt`'s volume: a subtle squeak), a corpse that fades. Real objects always come first, and nothing about a critter is ever sent. There are half as many as the habitats say (`DENSITY`, 2026-10-12).
  - **Birds and bats** (`packages/render/src/flyers.ts`, the Birds and Bats option under Ambient Life): no art in the game, so their silhouettes are drawn into a texture at startup (four wing beats each; bats two-toned so they read against rock). Points like the snow, sized by `setProjection` (drawing buffer height and FOV), hidden by walls in front, never picked, and left out of the glow pass (PostFx's list). Flocks cross 9-15 squares above us by day in rooms with any open sky (a sector with `ceilingType` 0); bats live only in caves, dungeons, crypts, prisons, Castle Victoria and Brax (`critters.ts batsOf`: `habitatOf` "cave" and "dungeon", NECROPOLIS terrain, `PRISONS`), flitting about head height, under the ceiling in cramped crypts and over floors near the player's level only (not the tops of a maze's walls); where such a room has sky (Brax's graveyard and ruins), a few fly low at night only. Birds and bats are drawn as they are in the texture, birds with their wings level and bats upright, ears up (birds used to turn to their heading on screen, and leaned). While the Browser pane shows the page, it animates live: placing things from a script gets them moved on the next frame.
  - **Nature** (`packages/render/src/nature.ts`, the Nature option under Ambient Life): butterflies over green country (FOREST, FIELDS, HILLS, JUNGLE) by day and not in the rain, fireflies there and by lakes, rivers and swamps at night, leaves falling in forests and jungles, and fish leaping from open water (a floor with a water texture, `watertextures.json`, and no ceiling: not every sector with depth, as the wheat fields and wet sand have one; a room needs about six squares of it, so no fish in puddles; none in sewers or caves) with a splash. All drawn in code into one texture, points like the birds'. Fireflies alone shine in the glow pass (`uGlowPass`), so the Nature group isn't in PostFx's skip list; the others draw black there.
  - **Ground Detail** (`packages/render/src/groundCover.ts`, its own option, not under Ambient Life): grass tufts and small flowers on grass floors, dry tufts on earth, and rocks: the game's own rock ornaments (`rocksm`, `rockla`, `boulder`, `rockb`, `molrock`, `rockc`, `rock`, `rock2`; `GameScene.loadRocks`, each for the grounds it suits), drawn at a fraction of their size (mostly pebbles, never bigger than the ornament: `ROCK_SIZE`), and rare (a rock in about 27 half-square cells of rocky ground, 36 of earth, 200 of grass); none in towns, castles, guild halls, temples and shops (`SETTLED` terrain, or a room in `ambientRooms.ts`: the castles' rooms mostly have no terrain), and none on cobbles or flagstones (`isCobbled`: deep dark mortar lines and strong contrast) but in caves. Under open sky and in caves, within 20 squares (shrinking away past 15). The floor's kind, colour and cobbles come from `floortextures.json` (`classifyFloor`, `isCobbled`). Where each piece stands is a hash of the room's name and its half-square cell, so everyone sees the same ones. Two layers of opaque, alpha-tested points (the tufts tinted by the floor's colour, the rocks in their own colours): no sorting.
  - **The storm** (with the Weather option): puddles (`packages/render/src/puddles.ts`) spread on open ground under the sky as the rain goes on (`gameScene.wetness`, 45 s to full, 150 s to dry), hashed by room and square like Ground Detail, on level ground only, rings where drops fall; the same rings fall on open water under the sky while it rains (whole squares of a sector with depth or a water texture, within 12 squares, added so they only lighten: `Puddles.ringSquares`). They're flat quads in a scene that mirrors handedness, so they're drawn double-sided. Lightning (`lightning.ts`) strikes 45-70 squares off every 5-18 s while it rains under open sky: a ribbon bolt about the camera, hidden by walls in front, glowing in Enhanced's glow pass; the sky darkens in the rain (`OVERCAST`) and flashes with each strike, and so does the view (`.lightning-flash`). In dev, `session.world.effects.raining = true` and `gameScene.wetness = 1` show them at once.
  - **Ambient sounds** (`apps/client/src/game/ambientSounds.ts`, the Ambient Sounds option and its volume; [docs/ambient-sounds.md](docs/ambient-sounds.md) lists every cue): chatter under the crowds, the arena's fights (`arenaEvent`: the game's own hit, cry, spell and frying sounds) and cheers, thunder after lightning, critters, fish splashes and puddle steps (birds, bats, butterflies, fireflies and leaves are silent), only where people live (`AmbientSoundFrame.populated`: a room in `ambientRooms.ts` or `SETTLED` terrain); the wilds keep the original's sounds alone, but for thunder with the lightning. They play through `GameAudio.playAmbient`, a bus and voices of their own (`MAX_AMBIENT`), so they never take the server's 24. The scene drains what happened each frame (`AmbientLife.takeEvents`, `ArenaView.takeEvents`, `Lightning.takeStrike`, `Nature.takeSplashes`) whether heard or not. Recordings that aren't the game's are CC0, fetched by `npm run sounds` into `dist/sounds` (never in git) and copied by `npm run assets` as `amb_*.ogg`. Dev: `gameScene.ambientSoundBoard.audition("thunder")`. New sounds are auditioned by the user before they stay.
  - **Seasons** were tried and taken out: the server has them (`system.kod GetSeason`, the game year) but never sends them to the client.
  - Where they go: `roomexits.json` (door squares, edges, and the squares other rooms' exits put you on), built from the Kod rooms by `npm run assets`; rebuild after changing a room's exits. Which rooms get them, and how many: `ambientRooms.ts`.
  - Nav grids are built once by `npm run assets` for every room in `ambientRooms.ts` (`nav/<room>.nav`, `encodeNavGrid`), checked against the room's checksum when read (`decodeNavGrid`); a missing or stale one is built in the client a slice a frame. `GameScene.navGrids` keeps the last 8 rooms' grids for the session. Bump `NAV_FORMAT` when the grid's rules change, and rebuild the assets.
  - Paths (`navGrid.ts`): half-square cells centred on squares' centres and corners (so a one-square door has a row down its middle), kept 280 fine units from walls that stop a player (`move.c`'s rule, judged once per wall side), linked when 260 clear. `AmbientLife` builds the grid in 3 ms slices. `ambient.test.ts` walks a `PlayerMover` along Tos's paths; the odd long line grazes a corner because `move.c`'s steps truncate.
  - In dev, `window.shards.gameScene.ambientLife` has `objects()`, `paths()` and `nav`. While the Browser pane is hidden, drive it with `gameScene.frame(dt, t)`.

- **The arena** (ours, [ADR 0007](docs/adr/0007-arena.md), its "As built" section has the details):

  - `AssetCache` follows the desktop's rules:
    - the APK's copy when the server's hash matches (release builds bundle `dist/assets` as `assets/assets/`);
    - then `filesDir/asset-cache/<name>.<hash>`;
    - then the server, checked against the hash.
  - The full download runs only on an unmetered network and never for the local dev stack. The cache and the download are per process: Android can create the activity twice.
  - The phone layout is `touch-ui` on `.game` (the `touchControls` setting, Auto: a coarse pointer, so phone browsers too; no longer in the Bind Editor, but `localStorage` `shards.settings` can force `"on"` for testing in a desktop browser). `ui/TouchControls.tsx` has the Modern interface's `UnitFrame` (our face, the green bars and our enchantments, top left: the two layouts look alike there), the first row of quick slots as a hotbar along the bottom between the joystick and the buttons (bigger for fingers, `.touch-hotbar --slot`: as big as fit, up to 50 px; a long press changes a slot, `Hotbar touch`), the joystick and the buttons.   - Dialogs with `wide` (`kit.tsx Window`: the character creator, Adjust your character) get up to 50% wider on a phone (`--w` stretches `--dx`; the text keeps its size), as far as the screen allows. Anything in them drawn square needs CSS for it (`.mk-face .face`).
